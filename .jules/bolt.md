## 2023-10-24 - Synchronous LocalStorage I/O Blocking Render
**Learning:** Performing synchronous `localStorage` reads (`getHistory()`, `getUpdates()`) directly in the render body of a React component (like `LibraryView.jsx`) creates severe main-thread blocking, especially noticeable during rapid state updates like text input (`searchQuery`). Combined with expensive deduplication and filtering arrays on each render, it causes the UI to freeze while typing.
**Action:** Always wrap expensive synchronous Disk I/O operations (like fetching from localStorage) and CPU-intensive array transformations/filtering inside `useMemo` hooks, keeping dependency arrays minimal to prevent re-execution unless the underlying data sources actually change.

## 2023-10-24 - Synchronous LocalStorage I/O Blocking Render
**Learning:** Performing synchronous `localStorage` reads (`getHistory()`, `getUpdates()`) directly in the render body of a React component (like `LibraryView.jsx`) creates severe main-thread blocking, especially noticeable during rapid state updates like text input (`searchQuery`). Combined with expensive deduplication and filtering arrays on each render, it causes the UI to freeze while typing. However, caching the `getHistory()` and `getUpdates()` calls behind an empty dependency array (`[]`) introduces a bug where the UI will permanently display stale data if the underlying data changes while the component is mounted.
**Action:** Wrap expensive CPU-intensive array transformations/filtering inside `useMemo` hooks, keeping dependency arrays minimal to prevent re-execution unless the underlying data sources actually change. For external data sources like `localStorage` reads that can change while the component is mounted, either fetch them on every render or implement a subscription/polling mechanism if performance demands it.
